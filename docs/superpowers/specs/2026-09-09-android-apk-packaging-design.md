# Packaging Hulaan Bayan as an Android release APK

**Date:** 2026-09-09
**Status:** implemented and verified, 2026-09-09

All six checks in *Verification* below were observed, including the deliberate
gate break: with the signing wiring sabotaged Gradle still reported
`BUILD SUCCESSFUL in 22s`, and only the marker gate stopped the unsigned APK
from being exported.

One pinned version in this document was wrong and was corrected during
implementation: JDK 17 was inferred from AGP 8.13's minimum, but
`@capacitor/android` 8.5.1 compiles at source/target 21, so the first build
failed with `invalid source release: 21`. The table now reads JDK 21.

## Problem

`game/Hulaan-Bayan-Game/HulaanBayan.py` cannot be compiled to an APK. It is a
Tkinter application, and no Android toolchain ships Tk — not
python-for-android/Buildozer, not BeeWare Briefcase, not Chaquopy. Tk needs an
X11, Win32 or Cocoa windowing layer that Android does not provide. Two further
blockers sit in the same file: `winsound` (line 9) is Windows-only, and the UI is
~1139 lines of module-level procedural code with 29 `Canvas.create_*` calls and
`.place()`-based absolute layout, none of which ports mechanically.

The repository already contains a complete, mobile-ready port of the same game —
`play.html` plus `assets/game-core.js`, `assets/words.js`, `assets/play.js` —
with a viewport meta tag, a tap keyboard and an SVG scaffold. Packaging that is
the cheap path to a real, signed release APK, so that is what this design does.

The Python desktop edition stays exactly as it is. Nothing in this design edits,
ports or deprecates it.

## Approach

Reuse the containerised Android build architecture from
`/home/ordrid/projects/work/eomis/geotagger`, substituting Capacitor for
Expo/React Native at the application layer.

The geotagger build architecture is what carries over, and it carries over whole:

- No bind mounts anywhere in the build path, so host file ownership is identical
  under rootless and rootful Docker.
- Gradle and package caches as `RUN --mount=type=cache`.
- Keystore and passwords as `RUN --mount=type=secret`, never in a layer, never in
  `ARG`/`ENV`, never in `docker history`.
- APKs exported through a `FROM scratch` stage with `--output type=local`, which
  BuildKit writes as the invoking user.
- `android/` treated as generated output: gitignored, regenerated every build,
  with signing re-applied by a script rather than hand-edited.
- Two gates that fail the build rather than emit a wrongly-signed APK.
- A `just` recipe surface with the same verbs.

What does not carry over is the Expo/React Native application layer. Geotagger
needs the NDK and CMake because `react-native-reanimated`,
`react-native-worklets`, `react-native-screens` and `expo-modules-core` all ship
`CMakeLists.txt` and compile C++. A static HTML game compiles no native code.

| | geotagger | Hulaan Bayan |
|---|---|---|
| SDK stage contents | SDK, build-tools, NDK, CMake | SDK, build-tools |
| SDK stage size | ~6 GB | ~2.5 GB |
| Total disk | ~12 GB | ~4 GB |
| `android/` generated by | `expo prebuild` | `npx cap add android` |
| Signing re-applied by | `plugins/with-release-signing.js` (Expo config plugin) | `scripts/apply-android-config.mjs` (plain Node) |
| ABIs | 4, each natively compiled | not applicable, no native code |
| Warm build | tens of minutes | ~2 minutes |

### Alternatives rejected

**Rewrite the UI in Kivy and build with Buildozer.** This is the only option that
yields a genuinely Python APK. It costs a full rewrite of all 1139 lines — every
screen, the canvas drawing, the `.place()` layout and the `winsound` audio — and
Buildozer's first build is slow and failure-prone. Rejected as disproportionate
to the goal, which is an installable APK of an existing, working game.

**BeeWare / Briefcase with Toga.** Same rewrite cost, and Toga's Android backend
is the least mature of the three with no canvas story close to what the bamboo
scaffold drawing needs. Strictly worse than Kivy for this shape of app.

**Capacitor without the container.** Requires an Android SDK on the host. On
NixOS the SDK's prebuilt glibc binaries (`aapt2`, `d8`, `apksigner`) need
`nix-ld` or `patchelf` to run at all. `nix-ld` is configured on this machine so
it would probably work, but "probably" is the problem: the containerised build
already exists, is already verified on this exact Docker installation, and moves
the question out of scope entirely.

## Web asset staging

The APK bundles a staged `www/` rather than the repository root. Staging is done
by `scripts/stage-www.mjs`, which runs inside the Docker build, so the repository
layout is untouched and GitHub Pages keeps serving precisely what it serves
today.

### What is included

`index.html`, `play.html`, `poster.html`, and `assets/` minus the exclusions
below.

### Page renaming, so the app launches into the game

Capacitor always loads `webDir/index.html` at startup; it has no start-page
setting. Launching into the game therefore requires renaming during staging, not
configuration:

| Repository file | Staged as | Role in the app |
|---|---|---|
| `play.html` | `www/index.html` | launch page — the game |
| `index.html` | `www/about.html` | project landing page |
| `poster.html` | `www/poster.html` | unchanged |

The inter-page link graph is small, entirely static and fully enumerated. No page
navigates via JavaScript — `location.href`, `location.replace`, `location.assign`
and `window.open` appear nowhere in `assets/*.js` or in any HTML file — so
rewriting the `href` attributes is sufficient and complete.

| In staged file | Rewrite | Occurrences |
|---|---|---|
| `www/index.html` (from `play.html`) | `href="index.html"` → `href="about.html"` | 2 |
| `www/index.html` (from `play.html`) | `href="index.html#developers"` → `href="about.html#developers"` | 1 |
| `www/about.html` (from `index.html`) | `href="play.html"` → `href="index.html"` | 2 |
| `www/poster.html` | absolute `.../play.html` → `href="index.html"` | 1 |
| `www/about.html` (from `index.html`) | `href="poster.html"` | unchanged, 1 |

`poster.html` links to the game by *absolute* URL. Under Capacitor that counts as
off-app and would open the system browser, pushing the user out to the website to
play a game they already have installed. It is made relative so navigation stays
in the app.

Rewrites are applied per-file after renaming, never as a global pass, because
`href="index.html"` means the landing page before the rename and the game after
it. A global substitution would conflate the two.

Each rewrite asserts its expected occurrence count and fails the build on a
mismatch, and a final pass fails if any `href="play.html"` survives anywhere in
`www/`. An edit that adds or removes a cross-page link fails the build rather
than shipping a link that loops back to the game or dead-ends.

### What is excluded, and why

| Excluded | Size | Reason |
|---|---|---|
| `assets/game-audio.js` | 5.4 KB | Dead. No HTML file in the repository references it. |
| `assets/bayan-theme.wav` | 1.1 MB | Dead on web. Only `game-audio.js` would load it, and nothing loads that. The Python game uses its own separate copy under `game/Hulaan-Bayan-Game/assets/`, which is untouched. |
| `downloads/Hulaan-Bayan-Website.zip` | 5.2 MB | Not linked from any page. |
| `downloads/Hulaan-Bayan-Game.zip` | 1.9 MB | Linked from `index.html`, but see below. |
| `downloads/Hulaan-Bayan-Poster.pdf` | 1.6 MB | Linked from `index.html`, but see below. |

This takes the bundled payload from ~11.5 MB to ~1.4 MB.

### Download links

All three pages link into `downloads/`, not just the landing page — five links
in total, established by running the staging script rather than by reading:
`www/index.html` ×2 (the game zip), `www/about.html` ×3 (the zip twice, the
poster PDF once), and `www/poster.html` ×2 (the poster PDF and PNG). A
relative `<a href>` to a local file under Capacitor's scheme does not trigger
Android's download manager, so these links are non-functional inside a WebView
whether or not the files are bundled.

`stage-www.mjs` therefore rewrites both `href`s to their absolute
`https://jihoooon14.github.io/Hulaan-Bayan-Game/downloads/...` equivalents.
Capacitor's `shouldOverrideUrlLoading` fires an `ACTION_VIEW` intent for http(s)
URLs outside the app's scope, so these open in the system browser and download
normally. This requires no Capacitor plugin.

The rewrite is asserted, not assumed: the script fails if either link is absent
from the landing page or if any relative `downloads/` reference survives anywhere
in `www/`. A future edit that adds a third download link fails the build rather
than shipping a dead link.

### Offline behaviour

The game itself is fully offline. `play.html`, `game-core.js`, `words.js`,
`play.js` and `play.css` are bundled, and sound is synthesised in-process through
the Web Audio API (`assets/play.js:33`), not loaded from a file. Only the two
rewritten download links need the network, and they are explicitly external.

## Signing

Structurally identical to geotagger, with one difference in the failure mode
being guarded against.

`scripts/apply-android-config.mjs` runs after `npx cap add android`. It writes a
self-contained `android/app/hulaan-bayan.gradle` and appends one
`apply from: "./hulaan-bayan.gradle"` line to `android/app/build.gradle`.

The same file also sets `versionCode` and `versionName`. Capacitor does not take
these from `capacitor.config.json`, and `android/` is regenerated every build, so
they need re-applying by exactly the same mechanism as the signing config —
hence one script and one emitted Gradle file rather than two of each. This is why
the script is named for the project rather than for signing alone.
Appending a line is stable across template changes; regex-editing the
`buildTypes` block is not. The script is idempotent.

Credentials never pass through the script, through `capacitor.config.json`, or
through any generated file. The emitted Gradle reads two environment variables
holding *paths*, and loads the passwords from the properties file at Gradle
execution time:

| Variable | Points at |
|---|---|
| `HULAAN_RELEASE_KEYSTORE` | `/run/secrets/release.keystore` |
| `HULAAN_RELEASE_KEYSTORE_PROPERTIES` | `/run/secrets/keystore.properties` |

If either is unset the wiring stands down, matching the template's default.

### The failure mode, and why it differs from geotagger

Expo's generated `build.gradle` sets `release { signingConfig signingConfigs.debug }`.
If geotagger's wiring failed to apply, `assembleRelease` still succeeded and
still produced an installable APK, silently signed with the static Android debug
key. That is the silent failure `BUILD.md` §4 is written against.

Capacitor's template sets **no `signingConfig` on the release build type at
all**. An unwired build therefore emits `app-release-unsigned.apk`, not
`app-release.apk`. The failure is louder — the copy step fails on a missing
filename — but it is not self-explanatory, and a future Capacitor template could
add a debug fallback. Both gates are kept:

1. **Marker gate.** `hulaan-bayan.gradle` logs
   `HULAAN-SIGNING: release keystore active` at Gradle lifecycle level when it
   takes effect. The build greps the Gradle log for it.
2. **Certificate gate.** `apksigner verify --print-certs` runs on the produced
   APK. The build fails if the signer is `CN=Android Debug`, and equally if
   `apksigner` reports the APK is unsigned.

A third, earlier check in the `prepared` stage asserts that
`hulaan-bayan.gradle` exists and that `build.gradle` applies it — cheap to
discover there, expensive to discover after a full release build. A fourth
asserts that the APK's bundled launch page is the game, by grepping
`android/app/src/main/assets/public/index.html` for the keyboard element.

### Keystore

`just keystore` generates a self-managed keystore, deliberately not an
EAS-managed or Play-managed one, so nothing about signing depends on a cloud
account.

```
secrets/                    # mode 700, gitignored
  release.keystore          # PKCS12, RSA 4096, 10000 days, alias "hulaanbayan"
  keystore.properties       # storePassword / keyAlias / keyPassword, mode 600
```

Passwords are stored in plaintext in `secrets/keystore.properties` so that
`just release` runs unattended. This is the same posture as
`android/app/debug.keystore` and is a real exposure: anyone who can read the home
directory can sign as the project. `just release` reads the file at invocation,
so a password-manager shim can materialise it into a temp file later without any
Dockerfile change.

`just keystore` refuses to overwrite an existing keystore. Loss is unrecoverable
— the key is not derivable from the APK or the password — and an app installed
with the old key cannot be updated by a build signed with a new one.

## Layering

```
base        JDK 21 · Node 22.23.2 · bun 1.3.13        keyed on: Dockerfile
  ↓
sdk         SDK 36 · build-tools 36.0.0               keyed on: Dockerfile
  ↓
deps        bun install --frozen-lockfile             keyed on: package.json, bun.lock
  ↓
staged      scripts/stage-www.mjs -> www/             keyed on: scripts/, *.html, assets/
  ↓
prepared    npx cap add android + apply-android-config
                                                      keyed on: capacitor.config.json
  ↓
build-release   gradlew assembleRelease
  ↓
release-apk     FROM scratch — APK only
```

The SDK layer is an ordinary image layer rather than a cache mount, so a source
change never re-downloads it and it survives `docker builder prune`.

Editing a `.html` or `assets/` file invalidates `staged` downward, which re-runs
`cap add` and Gradle. That is acceptable at ~2 minutes; splitting `www/` staging
below `cap add` would be faster but would mean the generated `android/` no longer
matches the staged assets in a single stage, which is not worth the complexity at
this build duration.

Each build `RUN` deletes `android/app/build` in the same layer after copying the
APK to `/out`, so the build layer does not carry intermediates.

## Recipe surface

| Recipe | Effect |
|---|---|
| `just keystore` | One-time. Generate `secrets/release.keystore` + `keystore.properties`. Refuses to overwrite. |
| `just release` | Signed release APK → `dist/hulaan-bayan-release.apk`. Refuses to run without a keystore. |
| `just verify` | Re-run `apksigner verify --print-certs` against everything in `dist/`. |
| `just fingerprint` | Print the release keystore's own SHA-1/SHA-256. |
| `just shell` | Optional interactive shell for poking at Gradle by hand. The only recipe that bind-mounts, and therefore the only one that detects the Docker mode. |
| `just stage` | Run the staging script on the host, without Docker, to eyeball the link rewrites. |
| `just contents` | List what the APK actually bundles, confirming the exclusions held. |
| `just clean` | Remove `dist/` and `www/`. Does not touch `secrets/`. |
| `just disk` | Report image and cache sizes. |

Geotagger's `just dev` is deliberately **not** carried over. It builds an
`expo-dev-client` debug APK that loads its JS from a Metro server. There is no
Metro server here and no dev-client concept; a debug APK would offer nothing over
opening `play.html` in a desktop browser, which is already the fastest way to
iterate on this game.

## Verification

The design is not complete until these have been observed, not assumed:

1. `just keystore` produces a PKCS12 keystore; `just fingerprint` prints a
   SHA-256 that is not the Android debug fingerprint.
2. `just release` exits 0 and writes `dist/hulaan-bayan-release.apk`.
3. `stat -c '%U:%G' dist/*.apk` reports `ordrid:users`, confirming the no-bind-mount
   ownership property holds on this rootless daemon.
4. `just verify` reports a signer that is neither `CN=Android Debug` nor absent.
5. `unzip -l` on the APK shows `assets/public/index.html` (the game),
   `assets/public/about.html`, `assets/public/poster.html` and the game's JS, and
   shows no `bayan-theme.wav`, no `game-audio.js` and no `downloads/`.
6. A deliberate check that the signing gate works: temporarily break the apply
   line, confirm the build fails at the marker gate rather than emitting an
   unsigned APK, then restore.

Installation on a physical phone is out of scope for this session — it needs
`adb`, udev rules and a `nixos-rebuild`, all of which require sudo. The
documentation covers it; the session does not perform it.

## Out of scope

- Any change to the Python desktop game.
- An `.aab` bundle for Play Store submission. `assembleRelease` produces an APK
  for sideloading. Play submission would also change the keystore calculus,
  because Play App Signing holds the app signing key and a lost upload key is
  resettable through support.
- App icon and splash screen design. The build uses Capacitor's default launcher
  icon. `assets/logo.png` exists but is a 1.2 MB PNG with no adaptive-icon
  foreground/background split; generating a proper icon set is separate work.
- Installing on a device, which needs sudo for udev rules.
